Scaling to the "largest representable value"
(as http://linux.die.net/man/3/glcolor3ui suggests)
is right.

Shifting up to the top of the value
(as http://www.opengl.org/resources/faq/technical/color.htm does)
is wrong.

Wrong in way may pass for right at high bit depths, hiding the problem.
Maybe it even counts as an OpenGL gotcha?

It certainly got me and it got the writers of http://www.opengl.org/resources/faq/technical/color.htm too.

The docs on that page
"Again, use glColor3ui() (or glColor3us(), etc.) to specify the color with your values stored in the most significant bits of each parameter."
are wrong too. At least they are consistent and wrong in the same way as the example code.

We don't address  sprites by the corner. Firstly animations are composed of many different sized rectangles of pixels (cropped as near as possible to the shifting artwork) so the corner moves. Secondly, using the corner is not generally expressive of game programmer intent. Instead: every sprite has a "handle": a pixel  specified by the artist - a stable point that is tracked across animation frames that the programmer uses to place the animation on screen. (when the artist draws the animation the handle, for him, the handle is just located in the middle of the screen). Where this is depends on the type of object - whatever would be best for the programmer. For floor standing things it is generally their feet.

Nick (the artist) drew all the left and right facing things individually (rather than just drawing one and generating the other).

confirms this

the example for loop at http://www.opengl.org/resources/faq/technical/color.htm
suggests that if you set numPrims to 2^(redBits+greenBits+blueBits) you'll visit every color value

GL11.glColor3ub((byte)0, (byte)0, (byte)0xf8);

http://linux.die.net/man/3/glcolor3ui

http://www.opengl.org/resources/faq/technical/color.htm example code seems to be wrong.
Consider the case where the loop walks all colors i.e. when numPrims is  2^(redBits+greenBits+blueBits).
It never submits the largest representable value (e.g. 0xffffffff). It only submits the largest color component
shifted up to the top of the integer (e.g. 0xff000000). Consequently it never reaches full intensity because,
as http://linux.die.net/man/3/glcolor3ui says "Unsigned integer color components, when specified,
are linearly mapped to floating-point values such that the largest representable value maps to 1.0 (full intensity),
and 0 maps to 0.0 (zero intensity)."
